# S19: Deployment workflows

## Objective

Git builds, signed webhooks, releases, previews, approval and rollback contracts.

## Scheduling and dependencies

Target date: 2026-11-03 (Europe/Berlin). Status at planning baseline: Ready for dispatch.
Dependencies: None; independent characterization/module implementation.

Dependency completion means reviewed artifacts are available at an explicitly verified base commit. Do not fabricate sibling interfaces, merge unrelated branches or bypass failed prerequisites. For independent modules, use a standalone package with `[workspace]` and tests runnable with `cargo test --manifest-path <module>/Cargo.toml`; root workspace integration is a separate owned task.

## Write ownership

Exclusive paths: `modules/deployments/`. All other paths are read-only. The coordinator controls shared architecture/contracts, manifests and task ledger unless those exact files are explicitly assigned here. A later task using these paths starts only after the previous owner hands them off. Propose shared changes in your package README and report them rather than silently editing shared files.

## Required behavior and design

Read root AGENTS.md, docs/engineering/FEATURE_PRESERVATION.md, docs/engineering/VARIANT_DESIGN.md, docs/engineering/MODULE_CONTRACTS.md and docs/testing/TEST_STRATEGY.md. Preserve relevant capability IDs and valid user-visible variants. Use black-box observation and white-box design analysis to avoid needless reinvention; code reuse must preserve mandatory notices. Do not claim an operation happened when only a plan/config was generated. Expose unsupported behavior explicitly. Keep secrets out of logs, argv, fixtures and result bodies. Never change production or workstation host services.

## Unit verification

Signature verification, replay controls and state transitions. Include meaningful negative cases and state invariants, not only construction/serialization tests.

## Integration verification

Local git repo, real build runner and isolated release directories. Use actual dependencies in disposable fixtures. Test doubles may verify boundary failures, but cannot qualify real dependency behavior. Capture exact commands, dependency versions and sanitized evidence.

## End-to-end verification

Deploy known commit, serve it, rollback and verify prior content. If runtime prerequisites are not available yet, provide executable case definitions and record BLOCKED with the exact dependency. A blocked/unrun case is not a pass. Final acceptance requires actual observed user outcome.

## Delivery and exit gate

Commit and push a focused branch; create a PR against **master**, do not merge it, and report its URL. Link the task issue and capability IDs. Include changed behavior, unit/integration/E2E commands and observed results, blockers, fixture teardown and known limitations. Reviewable code without required real evidence remains implementation-complete at most, not capability-accepted. Do not change repository visibility/settings or unrelated dependencies.

The objective defines the initial bounded implementation slice. Track every owned capability above, including those outside the initial slice, as implemented/partial/blocked with exact missing behavior. Report a follow-on work item for missing behavior; never delete the requirement or mark the domain complete from one example. Variants require separate acceptance evidence.
