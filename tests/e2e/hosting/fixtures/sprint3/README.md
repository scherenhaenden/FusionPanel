# Sprint 3 Websites Functional E2E Fixture

This fixture is the Sprint 3 API-to-agent-to-Nginx functional lane for real static-site and reverse-proxy lifecycle behavior. Run it only after the API, UI, agent, and privileged Nginx helper changes have been integrated into the checkout. The fixture must be invoked by a non-root host user.

From the repository root, run:

```bash
bash tests/e2e/hosting/fixtures/sprint3/run.sh
```

The runner creates a mode-0700 lock directory under the validated `XDG_RUNTIME_DIR` (or a validated user cache directory if unavailable) and takes a nonblocking host-local lock, so concurrent worktrees cannot race over the shared Cargo target or frontend build output. It requires at least 4 GiB `MemAvailable` and checks the helper source, existing frontend/Playwright dependencies, Docker daemon, Docker usage, and free disk space before building. It rejects Docker contexts and `DOCKER_HOST` values that do not resolve to a local Unix socket. Before building any artifacts, it requires the Compose local logging driver to retain at least two files because that driver compresses rotated logs by default. It requires at least 10 GiB free on the checkout filesystem before Cargo starts, performs locked offline development builds of the API, CLI, agent, and helper from the current source checkout, then builds the frontend from its existing `node_modules`. It does not install host dependencies or run Cargo tests. Each run records the source commit, a SHA-256 digest of all fixture inputs and staged image build contexts, and the Docker Engine, Compose, and Buildx versions. It stages only each image's Dockerfile and entrypoint into temporary build contexts. Image builds use a uniquely named, run-scoped Buildx builder with a 512 MiB BuildKit cache GC cap; cleanup removes that builder and its cache without pruning any global Docker cache. It binds the API and managed Nginx ports to dynamically allocated loopback ports. Host writable fixture state is under a unique temporary directory; managed Nginx files live on a size-limited tmpfs inside the disposable node container. Compose creates no named volumes, caps each service's memory, CPU, and process count, and retains two bounded log files per service.

The three services are:

- `api`: the existing Sprint 2 API fixture image with the real API, CLI, and built frontend mounted read-only; SQLite is in a 64 MiB container tmpfs owned by the fixture UID. It shares only the disposable node's network namespace so the actual agent can use the API's required loopback HTTP boundary. The runner publishes the shared API and Nginx ports on dynamically assigned loopback-only host ports.
- `node`: the real agent, privileged helper, and foreground Nginx process in the same disposable container. The Nginx master and helper run as container UID 0; the container drops all capabilities and grants only `SETUID` and `SETGID` so Nginx can drop its workers to `www-data` and the entrypoint can drop the agent to a dedicated container UID/GID 2001:2001. The agent gets only supplementary group 2000 for connecting to the helper socket; `setpriv` clears its inheritable and ambient capabilities and sets `no_new_privs`. The agent can connect to `/run/fusionpanel-nginx/nginx-helper.sock`, which is root-owned, group 2000, and mode 0660; the socket directory is root-owned, group 2000, and mode 0750 so the agent cannot replace the socket. `/etc/nginx/fusionpanel` and its managed subdirectories are root-owned mode 0750 on a size-limited tmpfs, and a health check confirms the dropped agent identity cannot write there. The helper accepts the current versioned, bounded Unix-socket RPC contract and independently validates the managed tree. Nginx uses Ubuntu `nginx` package `1.24.0-2ubuntu7.19` ([Ubuntu package listing](https://packages.ubuntu.com/noble/nginx)) on the repository-pinned `ubuntu:24.04` base. Candidate validation is `nginx -t`; reload is `nginx -s reload -c /etc/nginx/nginx.conf` against the same running server. A container-scoped `net.ipv4.ip_unprivileged_port_start=0` lets generated `listen 80` vhosts work without `CAP_NET_BIND_SERVICE`. No host Nginx or service manager is used.
- `upstream`: a small real HTTP service using the repository-pinned image `nginx:alpine@sha256:785835ea65db4bba6f021acc0f3be91b0fef76a53fe41f8588c6698d2aed0606`, running as UID 65532 on unprivileged port 8080.

The Playwright journey uses the UI to create a static site and a reverse-proxy site, checks `POST`/`DELETE` response envelopes `{site, job}`, the list envelope `{websites}`, the detail envelope `{website}`, typed agent operation payloads, and terminal job/site states. It checks real HTTP content through Nginx, then creates a reverse proxy to `http://unresolvable.invalid`. That URL is syntactically valid input; the real Nginx candidate check must reject it before promotion. Existing static/proxy traffic and the unrelated test vhost must keep serving. The test then deletes both active sites, checks their routes return 404, and checks the unrelated vhost still serves its marker.

Before the browser journey, the runner calls `nginx -t -q` in the real node container with the same literal `.invalid` `proxy_pass` form and requires the pinned Nginx binary to report `host not found in upstream`. The failure case relies on Nginx resolving a literal `proxy_pass` hostname during config validation; Nginx's own issue tracker records an unresolved upstream causing configuration test failure ([NGINX ticket #1040](https://trac.nginx.org/nginx/ticket/1040)). This direct probe is retained in the runner log because the agent captures Nginx subprocess output when validating its candidate. The exact Ubuntu Nginx package is pinned in the fixture and its `nginx -v` output is retained in the container logs.

The runner verifies the direct Nginx probe reports `host not found in upstream`, confirms the failed site leaves no candidate or enabled managed config, saves bounded/redacted container logs, tears down only its Compose project, removes only the two image tags it created, verifies its containers, network, and volumes are gone, and removes only its own temporary directory. It does not prune global Docker resources. Successful-run logs are retained in `RUNNER_TEMP` or the selected temporary directory for the release evidence record.

This lane proves candidate validation rejection before promotion. It does not claim to exercise a failure after promotion during Nginx reload.

## Package Acceptance Blocker

The API and upstream run as unprivileged users, the agent stays unprivileged, and only the isolated node's helper and Nginx master use container UID 0. The agent has RPC access to the helper but no write access to the Nginx configuration tree. This lane exercises the real HTTP job/worker/helper/config/reload path and covers the development-binary privilege boundary. Package acceptance remains blocked until the installed helper/systemd units, managed include, and `ProtectSystem=strict` policy are exercised under their actual packaged service identities.
